Problem Statement

Enterprise fleet fuel card platforms receive natural language commands from fleet managers, drivers, and admins. Queries like "find nearest truck stop with DEF within 20 miles" or "disable my card 987654 forever" or "generate a fuel code" need to be classified into the right intent and have their slots extracted so the platform can route them to the correct API call.

The standard approach is GPT-4 via cloud API. But this has three problems for enterprise use: ongoing per-query cost at scale, data privacy risk (card numbers, emails, and operational data sent to external servers), and latency variance on cloud endpoints.

The question this project answers: can a locally-hosted small LLM match cloud API quality for structured NLU tasks?

Hypothesis tested: A well-prompted 3B parameter local model can achieve >85% intent accuracy on a business-specific taxonomy (8 intents, complex slot extraction), with 100% JSON schema compliance, replacing GPT-4 for this narrow task at zero marginal cost.

System Architecture

The system is a FastAPI service wrapping an Ollama inference backend. The prompt pipeline constructs a structured system prompt containing the intent taxonomy and slot schema, sends it with the user query, then validates and parses the LLM output through Pydantic.

User Query │ ▼ FastAPI Endpoint /classify │ ▼ Prompt Builder ├── System prompt with intent taxonomy ├── Slot definitions per intent └── Output schema (JSON) │ ▼ Ollama Local Inference ├── Qwen 2.5 3B (primary) └── TinyLlama 1.1B (baseline comparison) │ ▼ JSON Parser + Pydantic Validator ├── Schema validation ├── Type coercion └── Error handling (malformed output) │ ▼ Structured Response { intent, slots, confidence } │ ▼ Evaluation Pipeline → Metrics Store

Why Ollama?

Ollama provides a clean HTTP API over local model inference, same interface regardless of model. This made swapping Qwen for TinyLlama a one-line config change, which was critical for running controlled comparisons.

Why Pydantic for output?

Regex parsing of LLM JSON is fragile. Pydantic enforces the schema at parse time and gives explicit validation errors. It also coerces types, for example converting radius from a string to a float when the slot schema defines a numeric field.

Prompt Engineering Decisions

The system prompt was the primary lever for performance. The final architecture went through three major iterations:

  • V1: Naive instruction. "Extract the intent and entities from this fleet query." Result: inconsistent JSON structure, ~55% accuracy. The model invented slot names.
  • V2: Taxonomy injection. Listed all valid intents explicitly with one-line descriptions. Accuracy jumped to ~78%. JSON still occasionally malformed.
  • V3: Schema-first prompt. Included the full Pydantic-derived JSON schema in the system prompt alongside a few-shot example. Intent accuracy: 91.11%. JSON valid rate: 100%.
# System prompt structure (V3) — real intents from llm_extractor.py SYSTEM_PROMPT = """ You are a fleet management intent classification and slot extraction engine. Classify the user query into exactly one supported intent and extract relevant slots. Supported intents: - FUEL_SEARCH (find fuel stations by type, radius, amenities) - CARD_MANAGEMENT (activate / hold / block fleet cards) - CARD_UNLOCK (unlock a card — only when "unlock" is explicit) - USER_MANAGEMENT (deactivate users by email) - FUEL_CODE (generate / cancel / list / status) - PROMPTED_ID_MANAGEMENT (create / activate / change driver PINs) - NOTIFICATION_MANAGEMENT (enable / disable / details alerts) - UNKNOWN (analytics, reports, or unclear queries) JSON schema: { "intent": "UNKNOWN", "action": null, "merchant_type": null, // TS | GS | FS "fuel_type": null, // Diesel | Gas | CNG | LNG | DEF | Reefer "radius": null, "radius_unit": null, // "miles" | "km" "amenities": [], // ["ATM", "TrkPrkPave", ...] "card_number": null, "email": null, "pagination_action": null, "confidence": 0.0 } Return ONLY valid JSON. No explanation. No markdown. """
Key insight: Embedding the JSON schema directly (not a natural language description of it) reduced hallucinated slot names from ~30% of responses to 0%. The model treats the schema as a hard constraint, not a suggestion.

Evaluation Results

Evaluation was run on 45 manually prepared test cases covering all 8 supported intents, with varying phrasing complexity. Both models ran on the same hardware (local CPU), same prompt template, same Ollama version.

Metric Qwen 2.5 3B TinyLlama 1.1B
Intent Accuracy 91.11% 28.89%
Slot Accuracy 89.68% 20.63%
Exact Match Accuracy 77.78% 4.44%
Valid JSON Rate 100% 100%
Average Latency 4.4s 8.6s

TinyLlama's 100% valid JSON rate with 28.89% intent accuracy reveals a specific failure mode: the model learned to produce valid JSON with hallucinated intent values — structurally correct output, semantically wrong. This is why valid JSON rate alone is a misleading metric for structured NLU.

Qwen 2.5 3B's higher latency than TinyLlama despite being a larger model is explained by the hardware. The inference was CPU-bound, where Qwen's architecture incurs more per-token compute than TinyLlama's simpler architecture despite being faster at the task level.

What I'd Do Differently

  • Add a confidence threshold gate. Currently all outputs are returned regardless of confidence. A threshold below 0.7 should trigger a fallback or human review path, not a silent low-quality response.
  • Test Mistral 7B and Phi-3. Qwen 2.5 3B performs well but these models are worth evaluating, especially Phi-3 Mini which punches above its weight on instruction following.
  • GPU-accelerated inference. The latency numbers (4.4s) are CPU-bound. With a consumer GPU these would drop below 500ms, which changes the production viability story entirely.
  • Fine-tuning on domain data. The current approach is zero-shot prompting. LoRA fine-tuning on 500-1000 labeled fleet queries would likely push accuracy above 97% with a smaller model.
