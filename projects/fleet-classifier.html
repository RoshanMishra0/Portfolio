Fleet Management
Intent Classifier

A local 3B model turns fleet-management requests into validated JSON. A deterministic rule layer around it lifted exact match on a held-out set from 73.3% to 88.9%.

Type Self-hosted AI service
Stack Python, FastAPI, Ollama, Pydantic, Docker
Model Qwen 2.5 3B
GitHub →

Demo

Problem

Fleet fuel-card platforms receive plain-language requests from fleet managers, drivers and admins: "find nearest truck stop with DEF within 20 miles", "disable my card 987654 forever", "generate a fuel code". Each one has to be classified into the right intent, with its details extracted, so the platform can call the right API.

A cloud LLM can do this, at a per-query cost and with card numbers and email addresses leaving the building. The question here: can a small model running locally do the job reliably enough?

Measured on 45 held-out queries covering all eight intents. None of them was used to write the prompt or the rules.

Architecture

User query │ ▼ FastAPI POST /classify │ ├── report or bare pagination request ──▶ rule answer, no model call ▼ Prompt intent definitions, slot mappings, worked examples │ ▼ Qwen 2.5 3B on Ollama JSON mode, temperature 0 │ ▼ Rule layer ├── map the action to the allowed business value ├── keep valid slot values, replace invalid ones └── clear slots that do not belong to the intent │ ▼ Pydantic validation │ ▼ Structured response intent, slots, source, latency

Why a Rule Layer

On the original 45 test cases the model alone scored 77.78% exact match. I went through the ten failures one by one:

FailureCasesExample
Action missing or not mapped to the business value5"remove card 5555" returned remove, expected block
Report or bare pagination request classified as a notification request4"generate fuel usage report"
Amenity list incomplete1"parking" returned one code instead of three

Every failure was a fixed rule the model did not apply, not a request it misunderstood. So the model keeps the job of working out what the user means, and code enforces the rules that never change.

Why the held-out set matters: with the rule layer the original test set scores 100%, but the rules were written from those same failures. That number proves nothing. The held-out result above is the one I quote.

What Still Fails

Five of the 45 held-out cases fail. I left them unfixed so the held-out numbers stay honest.

  • Lost or stolen card read as a user request (2 cases). "I lost my card 112233" is classified as user management. This is an intent error by the model; the rules only act after the intent is chosen.
  • Pagination with a business object (1 case). "show me another truck stop" is classified as a notification request.
  • Valid but wrong model value kept (2 cases). "show fuel codes" returned generate where list was expected. The rule layer keeps any model value that is in the allowed list; preferring an explicit word in the query would fix both.

The Prompt

The prompt carries the intent taxonomy, the slot schema and the value mappings. An abridged version:

# System prompt structure (V3) — abridged from fleet_intent/prompt.py SYSTEM_PROMPT = """ You are a fleet management intent classification and slot extraction engine. Classify the user query into exactly one supported intent and extract relevant slots. Supported intents: - FUEL_SEARCH (find fuel stations by type, radius, amenities) - CARD_MANAGEMENT (activate / hold / block fleet cards) - CARD_UNLOCK (unlock a card — only when "unlock" is explicit) - USER_MANAGEMENT (deactivate users by email) - FUEL_CODE (generate / cancel / list / status) - PROMPTED_ID_MANAGEMENT (create / activate / change driver PINs) - NOTIFICATION_MANAGEMENT (enable / disable / details alerts) - UNKNOWN (analytics, reports, or unclear queries) JSON schema: { "intent": "UNKNOWN", "action": null, "merchant_type": null, // TS | GS | FS "fuel_type": null, // Diesel | Gas | CNG | LNG | DEF | Reefer "radius": null, "radius_unit": null, // "miles" | "km" "amenities": [], // ["ATM", "TrkPrkPave", ...] "card_number": null, "email": null, "pagination_action": null, "confidence": 0.0 } Return ONLY valid JSON. No explanation. No markdown. """

Earlier Experiments

These runs came before the current repository and their result files are not in it.

Prompt iterations

  • V1, plain instruction. "Extract the intent and entities from this fleet query." About 55% accuracy, with inconsistent JSON and invented slot names.
  • V2, taxonomy listed. All valid intents listed with one-line descriptions. About 78% accuracy; JSON still occasionally malformed.
  • V3, schema first. The full JSON schema in the prompt with worked examples. 91.11% intent accuracy and 100% valid JSON on the original test set.

TinyLlama produced valid JSON every time and the right intent less than a third of the time: structurally correct, semantically wrong. Valid JSON rate alone says very little about a structured-output system.

Built to Run

Service

Health and readiness checks, model warm-up at startup, 503 on model outage, and logs that record intent and latency but never the query text.

Engineering

About 50 unit and API tests that run without a model, GitHub Actions CI, pinned dependencies, and Docker Compose for the API and Ollama together.

Limits and Next Steps

  • Small test set. With 45 cases, one case moves a metric by about 2.2 points. The next step is a held-out set of 200 or more, with paraphrases and typos.
  • Latency. About 5 seconds per query is too slow for an interactive assistant. The full prompt is sent on every request; a shorter prompt and schema-constrained output are the first things to try.
  • Other small models. A side-by-side run against two other local models on the held-out set.
  • Confidence. The confidence field is the model's own estimate and is not calibrated.
