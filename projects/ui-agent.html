What Makes This Different from a Chatbot

Most "AI email assistants" are chatbots that answer questions about your inbox. This is something different: the AI controls the actual UI state. When you type "open the latest email from David", the assistant doesn't respond with a summary. It navigates the inbox, finds the email, and opens it. The UI changes.

A chatbot does

  • → "Your latest email from David is about the project update."
  • → Answers stay in chat
  • → User still has to navigate manually

This agent does

  • → Opens the email in the email detail view
  • → Fills compose fields with the right recipient + subject
  • → Applies inbox filters and updates the list
  • → UI state changes, not just chat state

Key Design Decisions

1. UI state lives in Zustand, not component state

The AI action planner returns a structured action object. For this to affect the UI, the entire application's navigation and form state needs to be accessible from a single store. Zustand gives the assistant layer a clean, synchronous interface to mutate UI state: navigate to a view, fill a field, apply a filter.

2. Human-in-the-loop confirmation for sends

When the assistant composes and addresses an email, it does not send automatically. A confirmation toggle is shown before the send action fires. This is a deliberate design for the highest-risk action (sending to a real person). Read, navigate, and filter operations execute immediately.

Design principle: Autonomy should be proportional to reversibility. Navigating to a view is instantly reversible, no confirmation needed. Sending an email to an external party is not reversible, so it gets a confirmation gate. The agent earns trust by respecting the stakes of each action.

3. Fallback to TypeScript parser if Python service is down

The Next.js app includes a local TypeScript action parser that handles common commands without the Python service. This means development doesn't block when the Python service isn't running, and a simple deploy without the Python service still provides basic functionality.

4. Real-time sync: webhook + polling

Gmail watch registers a Pub/Sub subscription that delivers push notifications on inbox changes. The webhook endpoint at /api/gmail/webhook updates the Zustand store when a new email arrives. A 20-second polling fallback runs when the webhook isn't available (local dev, no ngrok, etc.).

What I'd Do Next

  • Replace heuristic parser with LLM tool-calling. The current Python action planner uses heuristic intent parsing. Replacing it with a proper tool-calling LLM (with defined tool schemas for each action) would handle ambiguous commands, multi-step requests, and edge cases far better.
  • True push to UI via SSE/WebSocket. The current webhook updates state on the server but requires the client to poll or manually refresh for inbox changes. Server-Sent Events from the Next.js API route would give instant UI updates on webhook receipt.
  • Thread/conversation view. Gmail's data model is thread-based. The current implementation shows individual emails. Grouping by thread and handling the full conversation context would make the assistant's "reply to this" action significantly more useful.
  • Confidence-gated actions. Low-confidence action plans should surface a clarification prompt rather than executing a best-guess action. "Did you want to filter by Sarah as sender, or search for emails mentioning Sarah?" would avoid wrong actions.
