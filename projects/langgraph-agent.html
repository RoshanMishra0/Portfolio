Why LangGraph Over Plain LangChain

LangChain chains are linear, one step feeds the next. This works for simple RAG pipelines but breaks down when agent behaviour needs to be conditional: retry a tool call on failure, loop until a condition is met, branch based on intermediate output, or return to an earlier node.

LangGraph models agent execution as a directed graph where nodes are processing steps and edges carry state. This makes non-linear agent behaviour explicit and inspectable. You can see exactly which path execution took and why.

LangChain Chain

Good for: linear pipelines, simple RAG, sequential transforms. State is implicit. Hard to add retry, branching, or loops without hacks.

LangGraph

Good for: agents with tools, conditional routing, multi-step planning, error recovery. State is explicit. Graph structure is inspectable.

Agent Architecture

The agent implements a ReAct (Reason + Act) loop within a LangGraph state graph. The key design decision: each node receives the full state object, does one thing, updates state, and returns. Routing logic lives on edges, not inside nodes.

START │ ▼ ┌──────────────┐ │ Planner Node │ ← Analyzes query, decides if tool needed └──────┬───────┘ │ ┌──────┴───────────────────────┐ │ edge condition │ ▼ ▼ Tool Call Node Responder Node │ calls tool(s) │ generates final answer │ updates state │ ▼ END Tool Result Node │ parses result │ appends to message history │ ▼ (loop back to Planner) ┌──────────────┐ │ Planner Node │ ← re-evaluates with new tool output └──────────────┘ │ ┌──────┴───────┐ │ │ Tool Call Responder ← when no more tools needed │ END Max iterations guard prevents infinite loops
Key design principle: The Planner node decides whether to call a tool or generate a final response. This decision lives in one place (the conditional edge from Planner), not scattered across multiple nodes. Makes the routing logic easy to test independently.

State Design

State management is the hardest part of building agents. LangGraph state is a TypedDict (or Pydantic model) that gets passed between nodes. Getting the state schema right determines whether the agent is debuggable or opaque.

from typing import TypedDict, Annotated, Sequence from langchain_core.messages import BaseMessage import operator class AgentState(TypedDict): # Message history — annotated reducer merges lists on update messages: Annotated[Sequence[BaseMessage], operator.add] # Tool outputs stored for reference by later nodes tool_outputs: list[dict] # Tracks how many tool calls have been made (loop guard) iteration_count: int # Set by Planner — "call_tool" | "respond" | "error" next_action: str # Final structured output final_response: dict | None

The next_action field is critical. The conditional edge from Planner reads this field to decide routing. By making the routing decision an explicit state field (not a return value from the node), any node can inspect why a particular path was taken.

Tool Calling Architecture

Tools are registered as LangChain tools with Pydantic input schemas. This gives the LLM a typed function signature it can reason about: it knows what arguments a tool expects, and the framework validates inputs before execution.

from langchain_core.tools import tool from pydantic import BaseModel class VehicleStatusInput(BaseModel): vehicle_id: str include_history: bool = False @tool("get_vehicle_status", args_schema=VehicleStatusInput) def get_vehicle_status(vehicle_id: str, include_history: bool) -> dict: """Get current status and location for a specific vehicle ID.""" # Tool implementation — database call, API call, etc. return fleet_db.query_vehicle(vehicle_id, history=include_history)
  • Typed inputs prevent silent failures. The LLM sometimes passes arguments in the wrong format. Pydantic validation catches this before the tool executes and returns a structured error the agent can reason about.
  • Tool output is stored in state, not just returned. Storing all tool outputs in AgentState.tool_outputs means any subsequent node can reference previous results without re-calling the tool.
  • Tool errors are handled in the graph, not inside tools. Tools raise exceptions; the Tool Result Node catches them and writes a structured error to state. The Planner then decides whether to retry, use an alternative tool, or respond with a partial answer.

Beyond the Happy Path

Most LangGraph examples show the happy path. These are the things that matter once an agent meets real inputs:

Iteration guard

The agent cannot loop indefinitely. iteration_count is checked on every Planner entry. At max iterations, the graph forces a transition to Responder with whatever partial state exists. No infinite loops possible.

Structured final output

The Responder node doesn't return a raw string. It writes a typed final_response dict to state with defined fields. The API layer reads this, not the raw message history.

Observable execution

Every state transition is logged. The next_action field creates a readable execution trace. You can replay exactly which path the agent took and why for any given input.

Error recovery path

Tool failures write to state as structured errors, not exceptions that bubble up and crash the graph. The Planner can route to an error recovery node or respond gracefully with partial results.

What I'd Do Differently

  • Add LangSmith tracing from day one. Debugging agent execution from print statements is painful. LangSmith's trace view makes the graph execution immediately visible. It should be set up before writing the first node, not after.
  • Separate tool definitions from tool implementations. Currently the tool schema and business logic live in the same function. Separating them would allow the tool schema to be tested independently from the API calls it wraps.
  • Implement a checkpointing strategy. LangGraph supports state persistence via checkpointers. For long-running agents, this allows recovery from mid-execution failures rather than restarting from the beginning.
  • Test with adversarial inputs. The agent was tested with well-formed queries. Production agents receive malformed, ambiguous, and contradictory inputs. A systematic adversarial test set would reveal where the Planner's routing logic breaks down.
