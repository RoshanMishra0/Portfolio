SAP Role Assistant:
Enterprise RAG

A question-answering assistant over large Word, Excel and PDF repositories. Hybrid retrieval raised precision and recall on keyword queries from under 0.70 to over 0.85.

Role AI Engineer, Accenture
Type Production system for an enterprise client
Stack Python, Elasticsearch, Azure OpenAI, Claude, Docker, AWS ECS
Client name, documents, prompts and code are confidential and not shown

The Problem

Business users had to search large Word and Excel documents by hand to find the information they needed. The goal was an assistant they could ask in plain language and trust: answers grounded in the documents, and only in the documents each user was allowed to see.

Architecture

Ingestion Word / Excel / PDF │ ▼ Structure-aware chunking paragraphs, table rows, header-carrying spreadsheet chunks │ ▼ Embeddings Azure OpenAI text-embedding-3-small │ ▼ Elasticsearch vectors + text + access metadata Query User question │ ▼ Hybrid retrieval cosine similarity + BM25, scores normalised then combined │ ▼ Access filter only chunks this user may see │ ▼ Relevance check thresholds, LLM judge for borderline results │ ▼ Claude answer from the retrieved context only

Decision 1: Chunk by Document Structure

Fixed-size chunks cut tables in half and separate spreadsheet rows from the headers that give them meaning. I chunked each document type by its own structure.

  • Word. Paragraph-based chunks of roughly 500 characters. Tables are handled separately, with each row kept as its own unit.
  • Excel. Chunks of about ten rows, with the headers and sub-headers repeated in every chunk so a retrieved row still says what its columns mean.

Decision 2: Hybrid Retrieval

The first version used semantic search alone. It handled conceptual questions well and failed on exact business terms: SAP transaction codes, process abbreviations such as R2R and OTC, and customer identifiers. An embedding places those near similar-looking terms, which is the wrong behaviour when the user wants that exact one.

I found this by reading retrieval logs for the failing questions, not by adjusting the prompt. The fix was to combine semantic similarity with BM25 keyword search.

  • Normalise before combining. Cosine similarity and BM25 scores are on different scales, so each is normalised before the two are added.
  • Weight by query type. The balance between the two shifts with the kind of question being asked.

Decision 3: Access Control at Retrieval

The model is never asked to decide who may see what. Each chunk carries department and access metadata, and the retrieval query filters on the signed-in user's permissions. A chunk the user cannot see never reaches the model, so it cannot leak into an answer.

Principle: permissions are enforced by the search filter, which is deterministic, and not by a prompt instruction, which is not.

Decision 4: Keep Answers Grounded

  • Relevance thresholds. Results below a score threshold are dropped before generation.
  • LLM judge for borderline results. Results near the threshold get a second check on whether they answer the question.
  • Explicit uncertainty. The model is told to say when the retrieved context does not contain the answer.

Ingestion at Scale

95% less ingestion time

Embedding calls were batched and run in parallel, which cut the time to ingest the repository by 95%.

Hash-based change detection

Files are identified by a hash of their content, not by name or timestamp. A renamed copy is skipped; a changed file is re-embedded.

What I Took From It

  • Read the retrieved chunks first. Most wrong answers were retrieval failures, and the logs showed it before any prompt change could.
  • Exact terms need keyword search. Enterprise vocabulary is full of codes that embeddings blur together.
  • Measure retrieval on its own. Precision and recall against a fixed evaluation set made the hybrid change a number, not an impression.
