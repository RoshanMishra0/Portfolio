POAM Generator:
Agentic Compliance Automation

An agentic AWS workflow that writes compliance justifications for security vulnerabilities. About 29 minutes of analyst work per CVE became about 7 seconds.

Role AI Engineer, Accenture
Type Production system for an enterprise client
Stack Python, AWS Lambda, Bedrock, S3, EC2
Client name, prompts, data and code are confidential and not shown

The Problem

When a security vulnerability (a CVE) affects a system, compliance teams record how it will be handled in a Plan of Action and Milestones, or POAM. Business analysts were writing each justification by hand, at about 29 minutes per CVE, and the queue kept growing.

How the Workflow Decides

This is not one prompt that turns a CVE into text. The workflow first works out what each CVE needs, based on four things:

  • whether the CVE is valid,
  • whether a POAM already exists for it,
  • whether a report is required,
  • what is already stored for it in S3.

Only then does it call the model, with a structured prompt for that case, and write the result back.

Making Batches Fast Without Breaking Rate Limits

Running CVEs one after another took 14 minutes for about a hundred. Running them all at once hit the model provider's rate limits. The working design sits between the two.

  • Bounded concurrency. A fixed number of workers call the model in parallel.
  • Backoff and retry. A rate-limit response (HTTP 429) is retried with exponential backoff.
  • Scale down under pressure. When 429s increase, concurrency drops instead of piling on more retries.
  • Caching. Work that has already been done is not requested again.

Making It Reliable

Checkpointing in S3

Progress is written to S3 as the batch runs. If a run fails part-way, it resumes from the last checkpoint instead of starting again from zero.

Schema-validated output

Every response must parse and match the expected JSON schema before it is stored, which keeps the output auditable.

Recovering truncated JSON

Long outputs sometimes hit the model's token limit and came back as incomplete JSON. Retrying the whole workflow was slow and often failed the same way. The fix was targeted:

  • detect that the JSON is incomplete,
  • make a second call with a larger token allowance and a prompt written for continuation,
  • validate the final structured output before accepting it.
Principle: treat each LLM failure mode as its own case with its own recovery, not as a reason to rerun everything.

What I Took From It

  • The model is one step in a workflow. Most of the engineering was deciding what to ask, validating what came back, and handling what went wrong.
  • Rate limits set the design. Throughput came from controlled concurrency, not from maximum parallelism.
  • Long jobs must be resumable. Checkpoints turned a failed batch from a restart into a continuation.
